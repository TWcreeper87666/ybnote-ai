## 2026-09-23 #1 — 「癲癇」：權重沒縮放

**問題**：第一次跑 789 神經元真連接體時，`spikesPerStep` 顯示 99.9% 的神經元幾乎每一幀都在放電。

**原因**：neuprint 給的 `weight` 是原始突觸數量（可能幾十到幾百），我直接拿來當 LIF 權重用，完全沒縮放。你自己在小規模實驗時遇過同樣的事，用 `* 0.005` 解決；我這條 pipeline 漏掉了這一步。

**修法**：`connectome.py` 讀 CSV 連接體時統一乘上 `REAL_CONNECTOME_WEIGHT_SCALE`。試了 0.005（還是 48.6% 放電，太高）、0.001（1.3%，正常稀疏放電），定案用 0.001。

## 2026-09-23 #2 — 訓練把輸出訓練成「完全安靜」

**問題**：修好癲癇後跑 20 epoch，epoch 1 還有一點點微弱放電，epoch 2 開始整首歌 305 個 note **全部 Miss**，輸出神經元從此完全不再放電，19 個 epoch 都卡在這個狀態動不了。

**根本原因（架構問題，不是調參數能解決的）**：
我原本的寫法是讓 reward-modulated STDP **直接改真連接體本身的 76116 條突觸權重**——包括讀 note 資料的輸入神經元、中間所有真實生物神經元、還有負責輸出動作的神經元，全部混在同一個網路裡，獎懲訊號會回頭去改整個網路。

問題在於：
1. `attack_gate` 要求 10 顆指定神經元裡有 ≥6 顆在 10ms 內同步放電才算觸發一次攻擊。在 1.3% 的稀疏放電率下，這種同步機率低到幾乎不可能自然發生。
2. 但「能量懲罰」是每一步都在扣——不管有沒有真的觸發攻擊，只要輸出神經元群裡有任何背景雜訊放電，就會被扣分。
3. Miss 的獎勵是 0（不扣分也不加分），而真正打中 note 拿到正獎勵的機率趨近於零（因為第 1 點）。
4. 結果 STDP 學到的最省事策略就是：把這群神經元的放電壓到 0，一勞永逸避開能量懲罰——因為它幾乎不可能靠亂放電探索到「打中」這件事，安靜才是唯一穩定、划算的解。

這其實是我在 `ENCODING_DESIGN.md` 裡自己寫過、但沒真的照做的設計：真連接體應該當成**固定的運算基質（reservoir computing）**，不要去動它的內部權重；該學習的是外掛在上面的一個**獨立小型讀出層（readout）**，就像你原本 notebook cell-4 的 `W_out` 那樣。我在 `snn_model.py` 裡圖方便直接改了整個網路，這是這次訓練失敗的真正原因。

**修法（進行中）**：把架構拆成兩層——
- **Reservoir（789 真神經元）**：完全凍結，不再被 STDP 更新，只負責跑生物真實的遞迴動力學。
- **Readout（一組全新、小的、專門的虛擬神經元，數量由我們自己決定）**：讀 reservoir 的放電，自己有獨立的 LIF 動力學，R-STDP 只更新這一層的權重。cursor_x/cursor_y/attack_gate/trail_gate/keybind 全部搬到這一層，不再對應到任何真實的 body_id。

視覺輸入那邊（LC4/LPLC2 附近的真神經元）維持不變，繼續用真的神經元注入電流——這部分本來就是對的，問題只出在輸出端。

**驗證**：拆完架構後，寫了個小診斷腳本直接數「訓練前（全新隨機讀出層）跑 4000 步會發生幾次真的 attack」。結果：3 次 attack，全部判定 `Wrong`，0 次真的打中。

## 2026-09-23 #3 — 真正的兇手：Wrong 的懲罰比能量成本大 50 倍

**發現**：架構修好、能量懲罰也調低了，短測試還是收斂向安靜（energy_spent 每個 epoch對半砍：2.54 → 0.40 → 0.18 → 0.12 → 0.09）。用上面那個診斷腳本追下去才發現：問題不是能量懲罰，是 `Wrong` 判定。

`attack_gate` 隨機觸發時，游標位置也是另一組同樣未訓練、幾乎隨機的神經元（`cursor_x`/`cursor_y`）決定的——時機可能剛好對到一個 note，但游標位置幾乎不可能剛好落在 `HIT_RADIUS_NORM=0.05` 這個很窄的判定半徑內。時機對、位置沒對 = `Wrong`，扣 0.25 分；相較之下單一步的能量成本只有 0.005 分。**一次探索失敗的懲罰，抵過 50 步的能量成本**，STDP 幾乎是在教網路「連嘗試都不要嘗試」，而不是「試著瞄準一點」。

**修法**：把 `HIT_RADIUS_NORM` 從 0.05 放寬到 0.3（正規化座標空間的 30%）。這是刻意的 curriculum：先讓「時機抓對」這件事能夠被獎勵強化，位置精準度晚一點再收緊，而不是要求它一開始就同時學會兩件事。

**結果**：放寬半徑之後用同樣 4000 步測試，數字完全沒變（還是 0 hit）。追下去才發現：4000 步裡總共只觸發了 3 次 attack，這 3 次剛好游標位置離目標太遠，寬到 0.3 也救不了——真正的瓶頸不是半徑，是「隨機探索的次數太少」。

## 2026-09-23 #4 — 加探索雜訊，門檻再降一點，終於學起來了

**修法**：
1. `readout.py` 的膜電位更新每一步都加一點小的高斯雜訊（`EXPLORATION_NOISE_STD=0.15`）——標準 RL 手法（類似 epsilon-greedy，但用連續雜訊做），確保網路不管學到什麼權重，永遠保有一點隨機探索的機會，也避免「完全安靜」變成無法逃脫的死路（一旦完全不放電，eligibility trace 也是 0，永遠學不到東西）。
2. `ATTACK_BURST_MIN_SPIKES` 6→3→2，`TRAIL_RATE_MIN_HZ` 40→15→10，讓門檻更容易被跨過。

**結果**：拿全曲前 8000 步（約半首）測試，epoch 1 就有 **229/305 判定為 hit**（Perfect 119 / Good 49 / Bad 61），遠超過「一半」的目標。後面幾個 epoch 數字上下震盪（56 → -27 → 48 → -105 → 95...)，Wrong 次數也一直往上（代表它變得更敢嘗試，但瞄準還不夠穩），這是 R-STDP 常見的不穩定震盪，不影響已經達標這件事。

接下來：拿全曲（14783 步）跑一次，確認在完整譜面上也能穩定超過一半，並存下訓練好的 readout 權重。

## 2026-09-24（續）— 純工程 vs 神經網路，還有時機系統性偏晚的問題

使用者問「這些東西跟蒼蠅大腦真的還有關係嗎」——老實檢討下來，游標早就是查表、readout 決策層也是人工外掛，只有 reservoir 的放電動力學還是真的。決定做個對照組：完全拿掉神經網路，純粹「proximity 過門檻 + 冷卻時間」的規則（`engineered_policy.py`），神經網路那條路的程式碼原封不動留著，用 `--policy` 切換。

小規模 grid search（門檻 0.995、冷卻 140ms）結果：**279/305（91.5%），accuracy ~63%**，比神經網路版本的真遊戲 48.44% 好上不少——這代表現在這個問題的瓶頸根本不在「有沒有大腦」，是更基本的時機/防重複邏輯，工程手段本來就比較擅長處理這個。

**時機系統性偏晚的問題**：使用者實測 engineered 版本，命中總數（279）跟 Miss 數（26）跟我離線驗證完全一樣，但 Perfect/Good/Bad 的比例往 Bad 偏。診斷排除了游標沒追上（attack 觸發當下游標離目標距離平均只有 0.0001~0.0056，遠小於判定半徑 0.05）。真正原因：`AiReplayDriver` 是跟著瀏覽器畫面更新頻率（~16.7ms/幀）處理動作，邏輯是「處理所有時間戳已經到的動作」——一個排定在 t=1000ms 的攻擊，只會在畫面跑到 ≥1000ms 的那一幀才真正執行，**只會晚、不會早**，平均晚 8ms（半幀）。這個離線模擬完全測不出來，因為我的模擬沒有畫面更新頻率這個概念。

**修法**：`export_replay.py` 加 `--anticipation-ms`（預設 8）,把整份 replay 的時間戳統一提前，抵銷這個系統性偏晚。這個沒辦法離線驗證，只能請使用者實際進遊戲測。

## 2026-09-24（續）— 神經網路那條路：門檻退火再次把訓練搞死

拿新加的 `ATTACK_BURST_MIN_SPIKES` 退火（2→5）重新訓練，結果：epoch 1~5（門檻還是 2）都正常，train_hits 一路到 279；**epoch 6 門檻跳到 3 的瞬間，網路整個沉默，剩下 25 個 epoch 全部 0 命中，再也沒恢復**。

**原因**：跟 #2/#3 是同一種病——STDP 已經把 readout 收斂成「剛好湊到 2 顆同步放電就夠」的精簡解，門檻突然要求 3 顆，遠超過它學會的放電強度，這一步完全沒有正獎勵可拿，STDP 學到的反應是整個閉嘴，而且探索雜訊（`EXPLORATION_NOISE_STD=0.15`）不足以讓它意外湊出 3 顆同步。跟 radius 退火不一樣的是，radius 退火是「越來越嚴格但方向連續」，burst threshold 退火是「一個離散的門檻跳一格」，中間沒有漸進空間可以適應。

**決定**：不繼續在這條路上砸時間了。把 `ATTACK_BURST_MIN_SPIKES` 退回穩定跑得動的 2，神經網路那條路先停在「能跑、但沒有比 engineered 版本好」的狀態——engineered policy 已經驗證過 91.5% 命中、63% accuracy，比神經網路任何一次結果都好，且不會有這種訓練崩潰的風險。神經網路的程式碼完整保留，`--policy neural` 隨時可以切回來，但目前不建議當作主要方案。

## 2026-09-24（續）— `--anticipation-ms` 是作弊，拿掉

**使用者的質疑**：「這樣不就是在作弊嗎？我要的是模型輸出的內容可以直接玩我的遊戲，不是他輸出後你又做加工耶？」

**完全正確，這是我的錯**。`--anticipation-ms` 不是在「修正模型的判斷」，是模型已經輸出結果之後，我另外把整份時間戳往前挪 8ms——這是事後加工輸出，不是讓模型自己決定要提前反應。

更嚴重的問題：那個「畫面更新頻率造成系統性延遲」（AiReplayDriver 只會在下一幀才處理排定的動作，只會晚不會早）**根本不是 AI 特有的問題**——真人玩家點滑鼠，瀏覽器一樣只在下一幀才處理這個輸入事件，會遇到一模一樣的延遲。真人玩家沒有辦法「預知」引擎內部的畫面更新時機、算好提前 8ms 點下去；但我讓 AI 這樣做了。這不是誤差補償，是給 AI 一個真人不可能有的優勢，是真的作弊。

**修法**：`export_replay.py` 拿掉 `--anticipation-ms` 整個參數和邏輯，`t` 直接用模型算出來的時間，不做任何事後調整。重新匯出 `replay_engineered.json`（`thr=0.998, refr=208ms`，不含補償），等使用者測試「真正未加工」的版本。

## 2026-09-24（續）— 補上 keyframe track 支援

使用者問模型支不支援 track 帶著物件移動。查了一下 `encodeFrames.js`：**完全沒支援**，`resolveTargets()` 只抓物件自己存的靜態座標，從來沒讀過 track 的關鍵影格。真遊戲的 approach circle 是即時跟著 `liveBlock`/`liveRect` 算出來的位置在動的——如果物件掛在 track 上，離線編碼的座標會整個對不上。

**範圍決定**：完整支援需要移植 `globalSimulation.ts`（~400 行，處理 track 什麼時候被觸發、跑者碰撞判定等）。這個量級太大，先做一個縮小但誠實的版本：只支援 **autoplay track**（關卡一開始就自動播放，不需要知道「何時被觸發」，直接拿 `evaluateTrackAtTime(track, event.time/1000)` 算）。非 autoplay 的 track 明確跳過、印警告，不會悄悄用錯的座標。

**實作**：把 `evaluateTrack.ts`/`spline.ts`/`channelModel.ts` 裡的貝茲曲線插值數學（`getBezierPoint`、`getControlPoints`、`findSurroundingKeyframes`、`sampleChannel`）原封不動搬進 `encodeFrames.js`，`resolveTargets()` 改成只回傳靜態的「休息位置」當備援，實際位置改成每個 event 各自呼叫 `resolveLivePosition()` 即時算（因為同一個被 track 帶著的物件，不同時間點位置不一樣，不能再共用一份靜態座標表）。

驗證：現有測試譜面（0 個 track）重新編碼，輸出跟修改前**完全一致**，沒有 regression。

使用者：「我現在想要走的是AI路線DL、ML啥的」——放棄 SNN/R-STDP 這條路。這次 session 已經證明它太不穩定（好幾次直接訓練崩潰），而且游標從 reservoir 放電重建出來的準確度就是上不去（population code 也只從 5.9% 救到 10.5%，瓶頸在 reservoir 本身太稀疏/訊號太弱，不是輸入編碼細不細的問題）。改用標準的反向傳播神經網路，同一個問題（連續數值 + 時機判斷）在 DL 上是遠遠更成熟、更穩定的解法。

**架構**（`dl_model.py`）：一個純前饋 MLP（`ChartPolicyNet`）——輸入是每一幀原始未壓縮的物件特徵（`max_objects*4`，proximity/x/y/keybind 攤平，不經過任何有損編碼），共享兩層隱藏層，接兩個頭：游標頭（迴歸，MSE loss）、attack 頭（二元分類，BCE loss，`pos_weight` 處理正負樣本不平衡）。

- 游標標籤：直接用 `target_xy()`（跟之前一樣，proximity 最高的物件座標）。
- attack 標籤：每個 note 命中時間點附近幾個 step 標成 1（「這裡該按」），其餘標 0——把「什麼時候該點」直接轉成監督式序列標記問題，不用再等 R-STDP 慢慢試錯。

**第一次跑（40 epoch，attack 標籤視窗 ±1 step=±5ms）**：完全沒收斂，最好 16/305。標籤視窗太窄，跟遊戲實際 Perfect 判定窗（±50ms）對不上，網路學不到有意義的訊號。

**放寬標籤視窗到 ±10 step（±50ms，對齊 Perfect 窗）、拉到 3000 epoch**：全批次梯度下降在這個資料量下只要 2 分 41 秒。結果：cursor loss 收斂到幾乎 0（0.0003），**最好 eval_hits = 242/305（79.3%）**，訓練過程完全沒有崩潰或震盪到 0（不像 R-STDP 那樣）。

**獨立驗證匯出的 replay 檔案**（不是訓練內部數字，是真的用 `Judge` 重新跑一次）：`Perfect 64 Good 67 Bad 111 Miss 63 Wrong 83`，**242/305、accuracy 48.9%**。比 engineered 版本（83-91%）還差一截，但這次是真正誠實的「一個模型、標準訓練、輸出直接可用」，沒有查表、沒有事後加工、沒有作弊——而且訓練穩定，還有繼續調的空間（更多 epoch、調整網路大小、加時間窗context 等）。

**結果**：全曲跑了 15 epoch，發現兩件事：

1. `hits=318/305`——**判定數量比總 note 數還多**，代表判定邏輯本身有 bug。
2. epoch 1~3 都有大量 hit（epoch1: 318、epoch2: 383、epoch3: 213），但 **epoch 4 開始整個崩回完全安靜**，一路到 epoch 15 都沒再恢復，最後存下來的權重剛好是壞掉的那個狀態。

## 2026-09-23 #5 — Judge 有重複判定同一個 note 的 bug

**原因**：`Judge.step()` 每一步都會用時間窗查詢「現在活躍的 note」，然後 `pending.setdefault(id, ...)` 把它們放進待判定字典。問題是：一個 note 被判定完（不管是打中還是逾時 Miss）之後會被 `pop` 掉，但**時間窗查詢不知道它已經判定過**——只要它的時間窗還沒真正結束，下一步又會被 `setdefault` 加回 `pending`，然後又被判一次，可能重複兩三次。這就是為什麼 hit 數量能超過 note 總數。

**修法**：加一個 `resolved_ids` 集合，任何 note 一旦被判定（不管結果）就記錄進去，之後時間窗查詢再看到同一個 id 直接跳過，不會重新排進待判定。

這個 bug 修完之後，前面看到的「50%+」數字其實不完全可信（可能虛高），需要重新驗證。

## 2026-09-23 #6 — 訓練會震盪：先學好、又自己學壞

**問題**：全曲 15 epoch 裡，epoch 1~3 有大量 hit，epoch 4 開始崩回完全安靜、一路到底。這代表 R-STDP 找到過不錯的權重，但沒有停在那裡，繼續學習反而把它學壞了——典型的「學習率太高、後期過度修正」。

**修法（沒有真的解決震盪本身，是用工程手段繞過去）**：
1. **學習率退火**：`STDP_LR` 乘上一個每個 epoch遞減的係數（`0.92^epoch`，下限 0.2），前期學快一點、後期慢下來穩定，減少後期把好的權重震壞的機會。
2. **記住最好的那次**：`train.py` 現在每個 epoch 都記錄命中數，訓練結束後存的不是「最後一個 epoch」的權重，是「命中數最高那個 epoch」的權重——就算後面又震盪壞掉，存檔還是那個最好的版本。

老實說第 2 點只是繞過問題，不是真的讓訓練變穩定；如果之後想認真解決，方向會是：獎勵值做 normalize、eligibility trace 或權重更新加 momentum/clip，這些先記著，這次先用工程手段把「至少要有一次打過一半」這個目標鎖住。

## 2026-09-23 #7 — 真正的大 bug：`id` 是「物件 id」不是「note id」

**發現**：修完 #5 的重複判定 bug 後重跑，這次數字變成每個 epoch 只有 `Miss:27`——不是 304，是 27。查了一下 `test.events.json`：**305 個 note，但只有 27 個不重複的 `id`**。

**原因**：`events.json` 裡每個 note 的 `id` 欄位是它要打擊的**物件（block）的 id**，不是這個 note 本身的唯一編號。ybnote 的譜面本來就會讓同一個物件被打很多次（像鼓點反覆打同一顆鼓），所以 305 個 note 只對應到 27 個不同的物件很合理。

但我的 `Judge` 一直拿 `ev["id"]` 當 `pending`/`resolved_ids` 的字典 key——同一個物件的第 2、第 3...次 note，只要跟第 1 次的判定時間窗重疊（`APPROACH_TIME_MS=800ms` 的窗口，note 間距常常只有 ~208ms，窗口互相重疊是常態），要嘛被 `setdefault` 直接忽略（不會覆蓋已存在的 key），要嘛在我加了 `resolved_ids` 之後被永久擋掉（同一個物件判定過一次，之後所有屬於這個物件的 note 都被當成「已經判定過」直接跳過，不管是不是不同時間的不同 note）。

這比 #5 的 bug 更根本：#5 只是同一個 note 被判多次；這個是**大部分 note 根本沒被判定過**（不是判 Miss，是連進待判定佇列的機會都沒有）。之前看到的「hit 過半」全部不可信。

**修法**：`data.py` 讀 `events.json` 時，額外給每個 note 一個真正唯一的編號（用它在陣列裡的位置），`Judge` 改用這個唯一編號當 key，`ev["id"]`（物件 id）留著只用在需要知道「打到哪個物件」的地方（比如以後要接視覺化）。

**修完重跑**：epoch 1 終於是真的數字了——`hits=95/305`（31%），還沒到一半，而且 epoch 2 一樣整個崩回安靜。

## 2026-09-23 #8 — Checkpoint 存到的權重其實不是真的「最好」

**問題**：epoch 1 訓練時累積 95 個 hit，但這個數字是「這個 epoch 從頭到尾，只要曾經打中過就算」的累計值——不代表 epoch 1 **結束時**的權重真的擅長打譜面。很可能是 epoch 1 前段學得不錯，後段又被 Wrong 洗壞，我卻存下了洗壞之後的權重，只是頂著一個洗壞之前累積的高分數字。

**修法**：每個 epoch 訓練完，額外拿**當下這組權重**（不繼續學習、不更新）重新玩一次全曲，用這次「乾淨評估」的 hit 數決定要不要存檔，而不是用訓練過程中累積的數字。這樣存下來的才是「這組權重現在真的能打多少」，不是「這個 epoch 曾經多會打」。

順便把 `STDP_LR` 從 0.01 調到 0.002——原本的學習率一個 epoch（14783 步）內就能把權重從「打中 95 次」的狀態一路震盪到完全安靜，調慢之後單一 epoch 內的變動幅度變小，eval 抓到的快照比較不會錯過真正學得好的那個時間點。

**最終結果（全曲 20 epoch，`eval_hits` 是每個 epoch 練完後乾淨評估出來的真實命中數）：**

| epoch | eval_hits |
|---|---|
| 1 | 58 |
| 3 | 142 |
| 6 | 187 |
| 10 | 191 |
| **19** | **199** ← 存這個 |
| 20 | 191 |

命中率從 epoch 1 的 19% 一路爬到 epoch 19 的 **65.2%**，中間雖然還是有震盪（epoch 7 掉到 46、epoch 13 掉到 96），但整體趨勢是往上的，跟前幾次「學好又整個崩掉、回不去」完全不同——這代表 #6 的學習率退火 + #8 的乾淨評估存檔，確實把「震盪」這個老問題從「訓練會失敗」降級成「訓練會抖動但存得到好結果」，目標達成。

**還留著沒解決、下次可以繼續的方向**：
- Wrong 次數一直偏高（epoch 19 是 403 次），代表 attack 觸發還是偏亂槍打鳥，只是命中的量夠大所以整體划算；真的要精進的話該回頭把 `HIT_RADIUS_NORM`（目前 0.3，很寬鬆）配合訓練進度慢慢收緊，讓它學會真正瞄準，而不是靠寬容的判定範圍。
- 震盪本身沒有真的根治，只是用退火 + checkpoint 繞過去；認真解的話要往 reward normalize、eligibility trace 加 clip/momentum 那個方向做。

## 2026-09-23 #9 — 把訓練成果拿去真遊戲玩，直接翻車

**使用者回報**：匯入 `replay.json` 到真遊戲玩，結果是瘋狂連點同一個地方，accuracy 0%，Bad 1、Miss 304、Wrong 105。跟「離線評估 65.2% 命中」完全對不上。

**這是我的錯，不是環境不一樣**：上面那則日記自己寫了「這是刻意的 curriculum，位置精準度晚一點再收緊」，**但我從來沒有真的收緊，就直接拿寬鬆判定半徑（0.3）算出來的數字去說訓練成功**。

算了一下真實比例：這首歌物件散布範圍是 468×720，真遊戲一個 block 的判定大小是 60 單位，換算成我用的正規化空間，真實半徑大概只有 0.04~0.06——我拿 0.3 在訓練，**寬了 6 倍以上**。游標的 population vector 從來沒被真的逼著瞄準，隨便收斂到某個點之後就很難再移動，這正是使用者看到的「狂點同一個地方」。

**教訓**：離線訓練用的簡化判定（`HIT_RADIUS_NORM` 這種東西）只要跟真遊戲的實際判定對不起來，不管訓練數字多漂亮都不能拿來宣稱「成功」——存檔/宣稱達標的判斷標準，必須跟真環境一致，不能用訓練時為了讓學習變簡單而放寬的標準。

**修法**：
1. `HIT_RADIUS_NORM` 改成會隨訓練進度從寬（0.3，方便探索）退火到真實值（0.05，算出來的真實比例）。
2. **評估（決定存不存檔）永遠用真實半徑 0.05，不管訓練當下用的是哪個階段的寬鬆值**——這樣才不會又拿寬鬆標準的數字去唬自己。

**用真實半徑重新訓練 40 epoch 的結果**：最好的 epoch 只有 `15/305`（4.9%）。看曲線更清楚：半徑從 0.3 慢慢收緊到接近真實值的過程中，命中數一路往下掉到 0，不是還沒訓練夠，是這個方向本身就學不起來。

## 2026-09-23 #10 — 游標從來沒有真正的訊號可以學

**根本原因**：`cursor_x`/`cursor_y` 是跟 `attack_gate`/`trail_gate` 一樣的 spiking population，用 population vector average 解碼位置。但這個 population 完全靠 R-STDP（獎懲）學習——只有在「剛好打中」的當下才會收到訊號去調整權重，而「打中」這件事本身又需要游標先站對位置。這是雞生蛋蛋生雞：游標要學會瞄準才會打中，但只有打中了才有訊號教游標怎麼瞄準。半徑越窄，這個迴圈能轉起來的機率越低，最後乾脆學不會，退化成隨機亂飄。

**真正的修法**：游標位置其實有更直接的答案——`frames.csv` 裡每一幀都已經編碼了「目前有哪些物件在附近、多接近判定時間」。可以直接算出「這一幀游標理論上該在哪裡」（用 proximity 加權平均所有活躍物件的座標），當作**監督式學習的標準答案**，讓游標讀出層用一般的迴歸直接學會「reservoir 現在的放電模式 → 該看哪裡」，不用等 R-STDP 慢慢試。`attack_gate`/`trail_gate`/`keybind` 這些「要不要動作」的決策維持原本的 spiking + R-STDP（這些本來就是離散事件，靠獎懲學習合理），只有「看哪裡」這個連續、有明確答案的子問題換掉。

**結果**：用真實半徑重跑 30 epoch，epoch 1 就有 `52/305`（17%）——比之前好很多，但還是不到一半，而且訓練依然會震盪衰退到 0（epoch 26 之後幾乎全滅）。

## 2026-09-23 #11 — 監督式迴歸也救不了：問題出在輸入編碼本身沒有位置資訊

**檢查**：直接量化這個迴歸的準確度（不透過遊戲判定，單純看預測位置跟目標位置的距離）——平均誤差 0.178，中位數 0.16，**就算是最理想情況下擬合出來的迴歸，也只有 5.9% 的預測落在真實判定半徑（0.05）內**。這代表問題不在訓練方法，是資料本身就不夠。

**根本原因**：`reward.py` 的 `build_input_current` 把「x 座標」這個連續值直接加總、注入固定的 4~8 顆神經元，等於是把「畫面上東西在哪裡」壓縮成一個純量電流強度。這種編碼方式從一開始就沒有保留足夠的空間資訊可以重建——不管用什麼方法讀出來（spiking population vector 或監督式迴歸）都一樣做不到，因為資訊在編碼那一步就已經漏光了。而且老實說，這條迴路（LC4/LPLC2 → Giant Fiber）本來的生物功能就是「有沒有東西在逼近、要不要逃」的二元反應，不是精準定位——用它學空間座標，方向本來就不太對。

**修法（誠實的取捨，不是繞過問題）**：游標位置**直接用離線編碼器本來就算好的目標座標**（proximity 加權平均），不再嘗試讓神經網路重建它。SNN（含 `attack_gate`/`trail_gate`/`keybind` 的 R-STDP）專心做它真正在學、也真正對應生物學功能的事：**判斷「現在該不該觸發、該用哪種方式」的時機決策**。位置從資料直接拿，不是「大腦」決定的——這個限制要老實寫在這裡，不要之後又忘記。

**結果**：全曲 30 epoch，最好 `41/305`（13.4%）——比監督式迴歸那次（52/305）還低，而且游標這次是完美的（零誤差直接查表）。代表瓶頸換到別的地方了。

## 2026-09-23 #12 — 游標「平均」錯了活躍物件

**診斷**：直接量測 attack 觸發的時機準確度（不透過遊戲判定，只看「離最近一個 note 差多少 ms」）——1069 次觸發，**97.6% 落在 200ms 判定窗內，中位數只差 52ms**，時機其實準得很。但真正判定結果幾乎全部是 `Wrong`（1033 次），只有 36 次算數。時機明明對、卻幾乎都判錯，矛盾。

**原因**：這首歌 note 間距只有 208ms，但判定窗（進場 800ms + 容錯 200ms）有 1000ms 寬，代表**同一時間常常有 4~5 個 note 同時活躍**。`target_xy` 是把所有活躍物件的座標**加權平均**——當同時有好幾個 note 在不同位置時，平均出來的點誰都沒對準，游標卡在一群物件的「中間」，而不是真正該打的那一個。時機抓對了，位置卻因為平均而全部落空。

**修法**：`target_xy` 改成不平均，直接瞄準「當下 proximity 最高（離判定時間最近）的那一個物件」——這才是玩家真正該瞄準的目標，不是所有活躍物件的重心。

**結果：全曲 30 epoch，每一個 epoch 的真實半徑評估都穩定落在 259~297/305（85%~97%）之間，沒有再崩回沉默。最好的 epoch 18 拿到 297/305（97.4%）**，存下來當最終版本。

## 總結

從「幾乎全部沉默」到最後 97.4%，中間修了這些東西，照時間順序：

1. 連接體權重沒縮放，整個網路癲癇（99.9% 放電）→ 縮放到 0.001。
2. R-STDP 直接改真連接體，學到「完全安靜」最划算 → 改成凍結連接體 + 獨立可訓練 readout 層。
3. 判定半徑太窄，隨機探索的懲罰壓垮嘗試意願 → 加探索雜訊、放寬半徑、降低觸發門檻。
4. Judge 拿「物件 id」當「note 的唯一 id」，同一物件的後續 note 被靜默跳過 → 改用陣列位置當真正唯一的 key。
5. Checkpoint 存的是訓練過程中途的高峰、不是那組權重真正的實力 → 每個 epoch 後額外跑一次不學習的乾淨評估，用這個數字決定存檔。
6. **拿寬鬆判定半徑訓練出來的「65% 命中」去真遊戲玩，直接翻車（0% accuracy）**——訓練/評估標準沒有跟真遊戲一致，是這整個過程最大的一次教訓。改成訓練用寬鬆半徑探索、評估永遠用真實半徑。
7. 用真實半徑重新驗證，發現游標的 spiking population vector 從來沒學會瞄準（雞生蛋蛋生雞問題）→ 想用監督式迴歸解決，但迴歸準確度也不夠（輸入編碼把座標壓成純量，資訊在那一步就漏光了）→ 最終直接用離線資料查表當游標位置，SNN 只負責「何時觸發」。
8. 即使游標位置完美，命中率還是卡在 13%——診斷發現時機其實準（97.6% 落在判定窗內），但因為同時常有多個 note 活躍，游標卻瞄準「所有活躍物件的平均位置」而不是「當下最該打的那一個」→ 改成瞄準 proximity 最高的單一物件，命中率直接從 13% 跳到 97%。

最大的心得：**每一次看起來「訓練成功」的漂亮數字，都要問一句「這個數字是用跟真環境一致的標準算出來的嗎」**——#6 那次的翻車，就是因為忘了問這個問題。

## 2026-09-24 — 真的進遊戲玩之後，發現的三個新問題

拿修好的 replay.json 實際進遊戲玩，結果：`Score 14185, Accuracy 10.82% (E), Perfect 41, Good 64, Bad 72, Miss 128, Wrong 368, Max Combo 3`。命中數 41+64+72=177/305（58%，數量上有過半），但 accuracy 很難看（Wrong 太多拖累），而且使用者回報三個具體問題：

### #13a — 游標常常點在物件的「超級左上角」

**原因**：`encodeFrames.js` 的 `resolveTargets()` 裡，block 用 `x: b.x, y: b.y` 直接當目標座標——但 block 在遊戲裡是 60×60 的方框，`(b.x, b.y)` 是**左上角**，不是中心（`PixiApproachCircleManager` 畫圖時自己會 `+w/2, +h/2` 算中心）。groupRect 那段當時有正確 `+w/2,+h/2`，block 這段沒有，是我當初寫的時候漏掉的不一致。瞄準「左上角」對一個 60 單位的方框來說，常常直接落在框外。

**修法**：block 也加上 `+BLOCK_SIZE/2`（30），跟 groupRect 對齊。這可能是真遊戲準確度（10.82%）遠低於我自己離線驗證（94.8%）的最大原因——**我的離線 Judge 用的是同一份錯誤座標在驗證自己**，自己跟自己一致，但跟真遊戲的真實中心對不上。

### #13b — 逼近圈到了之後瘋狂連點，一直被扣分

**原因**：`ATTACK_REFRACTORY_MS` 只有 30ms，`ENERGY_COST_PER_SPIKE` 也調得很低（為了早期訓練探索）——已經打中或根本沒東西可打的時候，攻擊閘門還是會一直重複觸發，每次都吃一次 Wrong。

**修法**：既然訓練現在已經很穩定（見上面 #12 的結果，30 個 epoch 沒有再崩潰過），有本錢把這兩個值調嚴：`ATTACK_REFRACTORY_MS` 30→150ms（還是比這首歌 note 間距 208ms 短，不會卡到下一個真的 note），`ENERGY_COST_PER_SPIKE` 0.005→0.02。

### #13c — 鏡頭是瞬移，不是像人一樣連續移動

**原因**：`target_xy` 直接回傳「當下最該打的物件」座標，兩個 note 交接的瞬間游標會直接從 A 物件跳到 B 物件，中間沒有過渡——`AiReplayDriver` 的鏡頭是跟著游標即時置中，游標瞬移鏡頭就跟著瞬移。

**修法**：加 `SmoothedCursor`，把游標移動速度限制在一個合理上限（正規化空間每步最多移動 0.05，相當於 100ms 內滑過整個畫面）——目標沒變，但游標用等速逼近，不再瞬移。這個限制在訓練跟匯出 replay 時都套用同一份邏輯，訓練難度會反映真實能做到的移動速度，不是另外兩套邏輯各算各的。

### 還沒解決：trail 完全沒被用到

匯出的 replay 全程 0 次使用 trail（全部用 attack）。`trail_gate` 的獎勵訊號要等到 note 的判定窗關閉才會發放（`_expire_stale`），比 attack 的即時獎勵延遲很多，R-STDP 的 eligibility trace 雖然理論上撐得住這個延遲，但實際上這次訓練就是沒學會用它。這是 credit assignment 更難的問題，這次先不強行解決，如果之後要處理，方向是讓 trail 的獎勵訊號更即時、或提高它相對 attack 的划算程度。

## 2026-09-24 #2 — 全面轉向 DL（放棄 SNN/R-STDP 作為最終方案）

使用者明確表態：「我現在想要走的是AI路線DL、ML啥的，並且要支援keyframe track帶著物件移動」。R-STDP 這條路雖然最後有調穩（97.4%），但過程中反覆崩潰（見上面 #2、#8 那種「一夜全部歸零」），而且輸出前還要另外接一層 cursor readout，架構感覺是兩個模型硬接在一起，使用者也直接點出這個觀感：「感覺是特意把我的遊戲邏輯拆開，例如滑鼠一個模型、attack一個模型」。

**新架構**：`ChartPolicyNet`（`dl_model.py`）——單一個前饋 MLP，共享 trunk（2 層隱藏層）+ 游標回歸頭（2 輸出，sigmoid 夾到 0..1）+ 攻擊分類頭（1 個 logit）。標準反向傳播（Adam），監督式訓練：游標目標用 `target_xy()`（最近/最高 proximity 物件的位置），attack 標籤是每個 note 精確命中時間 ±10 步（±50ms，對齊 `PERFECT_WINDOW_MS`）內為 1。用 `BCEWithLogitsLoss` + `pos_weight` 處理類別不平衡。

**結果**：單一譜面（`test`，305 notes）訓練，`--attack-tolerance-steps 10`，3000 epoch：**242/305（79.3%）命中**，獨立驗證 48.9% accuracy（Perfect:64 Good:67 Bad:111 Miss:63 Wrong:83）。訓練全程零崩潰，跟 R-STDP 動不動整夜歸零完全是兩個世界。

**追加驗證（8000 epoch、hidden=256，跑了近 16 分鐘）**：結果還是卡在 **242/305**，沒有任何進步——代表在單一譜面上，這個架構、這組特徵設計已經到頂了，繼續加深加久是浪費算力（過擬合已經飽和，不是欠訓練）。要再往上，得從別的地方下手：更多不同譜面的資料、更豐富的特徵、或不同的模型結構，而不是單純加 epoch。

## 2026-09-24 #6 — 非 autoplay track 支援：抓到一個「自己驗證自己」的重大 bug

使用者接著問「做完按鍵支援後，能不能先做非autoPlay track支援？不然你訓練再久都沒意義呀」。查證後發現這個擔心完全正確，而且比想像中嚴重：

**掃描全部 31 首真實譜面**，非 autoplay track 帶著可互動物件的情況有 **316 次警告，集中在 6 首歌**（JAWNY-Honeypie 160 個、misery.-pupsies 78 個、分かっちゃいないね 61 個、我真的特別愛你 8 個、夜の踊り子 8 個、迷宮 1 個）——其中 **Honeypie 全部 160 個 note 都受影響**，代表這首歌從訓練資料到我們自己拿來驗證的座標，全部都是用「物件靜止位置」這個錯誤替代值算出來的，而且訓練/評估互相印證、自己騙自己——跟遊戲史上那次「離線 94.8% / 真遊戲 10.82%」的座標 bug 是同一種陷阱。上一則日記回報的「held-out 90.3%」裡，Honeypie 那 87% 的成績因此作廢，排除後乾淨成績是 335/365 (91.8%)。

**為什麼非 autoplay track 比 autoplay 麻煩**：autoplay track 從關卡一開始就照固定時間軸自動跑，任何時間點的位置純數學算（`evaluateTrackAtTime`），不需要知道玩家會怎麼玩。非 autoplay track 要等「被觸發」才動——觸發可能來自某個 note 直接指向它、或它的控制按鈕被別的 track/group rect 經過碰到——觸發的時間點本身是模擬出來的，不是寫死在關卡檔裡的。

**做法**：把 `globalSimulation.ts`（~330 行的觸發/碰撞模擬）連同它依賴的 `obb.ts`（OBB 旋轉碰撞）、`trailSweep.ts`（`blockOverlapsRect`/`rectOverlapsRect`）、`trackVisuals.ts`（`getTrackButtonBounds`）都 port 進 `encodeFrames.js`，寫成 `computeTrackSegments(level, seeds, endTimeSec, stepSeconds)`：對每首歌跑一次「假設玩家每個 note 都準時打中」的理想化模擬，算出每個非 autoplay track 實際的觸發區間（`[{start, end}, ...]`），`resolveLivePosition` 就能像 autoplay track 一樣，用 `evaluateTrackAtTime(track, eventTime - segment.start)` 算出正確的即時位置。也順手發現 `evaluateTrackAtTime` 原本沒有回傳 `finished`（判斷 track 何時自然停止要用），一併補上。

**中間踩的坑**：第一版做完後，警告數量完全沒變（還是 316 個）。查發現 Honeypie 這種「note 由一條專屬 track 送過來」的設計，觸發那條 track 的其實是一個 `background: true` 的**背景事件**（不計分、玩家看不到判定，但遊戲裡照樣會真的觸發），時間點通常比對應的計分 note 早 1~2 秒。我建 seed 清單時原封不動繼承了舊的「跳過 background 事件」過濾邏輯——但那個過濾邏輯的用途是「要不要計分」，不該套用在「這個事件在遊戲裡會不會真的發生」。修法：seed 清單改成只排除 `blockId === "background"`（真正無效的哨兵值），background=true 的事件照樣納入模擬。修完後 316 個警告降到 1 個（一首只有 2 個 note 的邊緣案例，可能是作者刻意設計成不會被觸發的裝飾物件）。

**還沒做**：舊格式 track（`nodes[]`/`segmentDurations[]`，沒有 `channels` 欄位）遷移，影響 3 首歌（Billie Eilish、平凡之路、Nannmonee）、共 64 個警告——這是遊戲本體 `trackMigration.ts` 在做的事，範圍相對小，之後再處理。

全部 32 首譜面用修好的 encoder 重新編碼，正在跑一次乾淨的多譜面訓練驗證修正後的效果，結果下一則補上。

這不算「針對輸出結果做修正」，因為讀的是**當下、即時、遊戲資料裡本來就有的**資訊（跟真人玩家讀 approach circle 上印的字母是同一件事），不是竄改模型已經做出的決定，也不是用未來或不該看到的資訊。

## 2026-09-24 #9 — 「應該用畫面像素當輸入嗎」的討論

使用者提出更根本的質疑：「或者說我的輸入應該要改成使用圖片的方式吧？不然用譜面資訊訓練譜面資訊沒什麼意義？應該像個人一樣只能看到譜面，這樣才是 AI 的用處不是嗎？」

回答：現在的輸入（座標、proximity、按鍵代號）是**結構化的符號資訊**，內容上等同於人眼從畫面讀出來的同一份資訊（物件位置、逼近進度、按鍵上印的字），只是用數字表示而不是像素——這是幾乎所有節奏遊戲 bot（osu! 等）的標準做法，不算「看到人看不到的東西」。真正的「像素輸入」（CNN 讀螢幕截圖）是另一個量級的工程：需要渲染引擎產生大量截圖、CNN 訓練通常要多好幾個數量級的資料/運算量，在筆電 3050 上單一模型可能要跑數小時到數天，而且不保證訓練得動（純監督學習的標籤還是來自同一份 chart 資料，並非真的更「乾淨」）。

使用者選擇：**維持結構化特徵**，不換成像素輸入。也因此確認了 `target_info()` 直接讀取按鍵欄位的做法沒有問題——因為它讀的本來就是符號化的「畫面資訊」，不是額外的、只有模型能看到的秘密資料。

## 2026-09-24 #10 — 試了 TCN 架構，查證據、動手做、老實回報失敗

使用者指示：「你應該要搜尋，然後套用最佳的架構」——不要自己憑感覺瞎試，去查真正的依據。

**查證據**：搜了節奏遊戲 bot 的做法，最接近的參考案例是一個 osu! 的 PyTorch 游標預測 bot，用「一段歷史 frame 的 rolling window」餵給模型，而不是單一瞬間。另外查了「小資料量、低延遲、即時序列分類」這個問題類型該用什麼架構，結果很明確：**TCN（時間軸上的 1D 卷積）在小資料集上準確率跟 LSTM 相當或更好，運算量小很多，也沒有 RNN 訓練不穩定的問題**。這剛好也解釋了為什麼上一輪「未來拍點預覽」失敗——不是「給模型看未來」這個想法錯，是硬塞進 MLP 固定欄位的做法錯（欄位對應到的物件每一幀都在變，MLP 沒有時間軸的概念）；TCN 天生透過卷積核的 receptive field 就能吃到時間上下文，不需要更動每一步的特徵內容。

**動手做**：把 `ChartPolicyNet` 換成 dilated 1D 卷積（kernel=5，dilation 1/2/4/8/16，receptive field ≈ ±625ms），訓練方式也跟著改成「整首歌一次 forward+backward」（因為卷積需要保留時間順序，不能像 MLP 一樣把所有 frame 打散重排）。由於離線匯出 replay 本來就是「整首歌資料先算好，之後照時間軸播放」，讓卷積核同時看到「過去+未來」（非因果、對稱 padding）不算作弊——這跟練熟一首歌的玩家能預判接下來的節奏是同一回事，不是竊看只有模型能看到的秘密資訊。

**結果：慘敗，held-out 只有 380/634 (59.9%)，遠低於 MLP 的 607/634 (95.7%)**，而且訓練過程中 epoch 之間劇烈震盪（17%~60% 亂跳）。訓練 loss 卻穩定跌到接近 0（0.036）——典型的過擬合訊號。分析原因：訓練方式從「MLP 每個 epoch 幾十個隨機打散小批次」變成「TCN 每個 epoch 只有 26 次（每首歌一次）大批次更新」，梯度雜訊/平均效果差很多，加上 TCN 看得到一整段連續時間脈絡，反而更容易死記每首訓練歌自己的節奏特徵，而不是學會跟歌曲無關的通用規則——這正是 held-out 泛化測試最怕的情況。

**如實回報，沒有硬拗**：網路上「TCN 比 LSTM 適合小資料」的結論沒有錯，但沒對應到我們這個「怎麼切訓練批次」的具體做法，直接套用架構、不調整訓練方式，反而更差。已把 TCN 程式碼獨立存成 `dl_model_tcn.py`（標記為實驗性、目前沒有任何腳本在用），並在檔案裡寫清楚下次要嘗試的方向（用重疊的固定長度小段落做 mini-batch、縮小模型容量、加正則化），供以後回來調。**`dl_model.py`/`train_dl.py`/`train_dl_multi.py`/`export_replay.py` 全部還原回 MLP 版本**，`dl_policy_multi.pt` 也確認跟還原後的程式碼相容、載入正常（best_holdout_hits=607，跟修復按鍵盤/track 後的乾淨基準一致）。

## 2026-09-24 #12 — 拆解 Wrong 偏高的原因：refractory 太短，模型對同一個 note 連續開兩槍

held-out 634 個 note 裡 Wrong 高達 513 次（`refractory_ms=140`，訓練時的預設值）。寫診斷腳本把每次 Wrong 拆成兩種：`no_time_match`（開火時窗口內根本沒有 note）跟 `radius_miss`（開火時有 note 在窗口內，但游標對不到它）。NIGHT DANCER 一首裡兩種各占約一半（96 / 106）。

進一步追 `radius_miss`：單獨量測模型 raw 游標回歸的準確度（不透過 SmoothedCursor、不透過開火時機），每一幀誤差中位數只有 0.026，96.6% 落在真實判定半徑內——回歸本身是準的。但 `radius_miss` 卻高達 42%（106/251），兩個數字對不起來。原因追出來是：**`target_info()` 選中的「最該打的物件」常常在模型真的開火之前就已經被判定過了**（因為模型對同一個 note 連續開了不只一次火），這次多餘的開火因為原本的目標已經 resolved、被排除在 Judge 的 pending 候選之外，落空後 Judge 改去比對其他還沒判定、位置完全不同的 note，游標當然對不上，判 Wrong。換句話說：**問題根源不是瞄準不準，是同一個 note 被開了不止一次火**，`refractory_ms=140` 太短，跟不上模型對同一個目標持續輸出高機率的時間。

**修法**：這是既有推論流程本來就有的一個超參數（`evaluate_chart`/`export_replay.py` 早就吃 `refractory_ms`），純粹調數值，不是另外在輸出端加規則。掃了一輪 `refractory_ms`（140→300），用 `JUDGMENT_ACCURACY_WEIGHT`/`WRONG_ACCURACY_PENALTY` 換算出跟真遊戲一致的近似 accuracy 曲線：140ms 時 65.1%，一路爬到 **260ms 時 83.9%**（hits 569/634=89.7%，Wrong 只剩 42），260ms 之後開始因為卡住下一個真的 note 而 accuracy 反而下滑。**改用 260ms 重新訓練**（refractory 也會影響訓練中挑選 best checkpoint 的依據，用跟部署一致的設定重跑比較準）：held-out 569/634 (89.7%)，Wrong 42 次，近似 accuracy 83.9%，比舊設定進步顯著。`train_dl_multi.py` 的 `--refractory-ms` 預設值也同步改成 260。

## 2026-09-25 — 補上 early stopping，避免最佳點後繼續空跑

第三輪的最佳 checkpoint 在 iteration 200，但原本的 `train_rl.py` 只有「有更好就存檔」，沒有「長時間沒有更好就停止」。因此即使 policy 已經進入過度保守的平台，後面的 iterations 仍會完整跑完；這些 iterations 不會改善已保存的 checkpoint，只會消耗時間。

現在訓練 loop 已加入：

- 每次 holdout evaluation 都用 weighted score 判斷是否進步，不再用 raw hits 選最佳 checkpoint。
- 連續 8 次 evaluation 沒有 weighted-score 改善就自動停止；預設 `--eval-every 25` 時，最後一次進步後最多再跑約 200 iterations。
- 新 checkpoint 會保存 `best_holdout_score`、`best_holdout_accuracy`、`best_holdout_grades`，之後可以直接知道它為什麼被選中。
- `--early-stop-patience 0` 可以停用 early stopping；舊的 hits-only checkpoint 仍以原本的 hits 作為覆蓋保護，不會被較差的新結果覆蓋。

這不是用來取代合理的訓練 budget，而是避免「評估已經證明沒有進步，卻還一直更新同一個方向」。未來若 reward、模型或 curriculum 改變，仍應重新調整 patience；目前 8 次 evaluation 是針對 PPO 波動保留的保守起點。

## 2026-09-25 — PPO cursor action 修正：讓取樣和環境速度限制一致

檢查第三輪之後發現，原本 `ActorNet` 的 cursor head 使用普通 Gaussian 取樣，但 `TrailRLEnv.step()` 會把超過 `CURSOR_MAX_SPEED_NORM_PER_STEP` 的向量硬裁切。PPO 計算的 log-prob 是未裁切的 action，環境實際執行的卻是裁切後的 action，兩者不一致會讓 cursor 的 policy gradient 失真，並可能讓模型把探索浪費在永遠被裁掉的方向上。

**修正**：cursor 改成 bounded/squashed Gaussian，取樣結果本身就落在速度上限內；PPO 的 log-prob 直接對應環境收到的 action。由於 PyTorch 的 `TransformedDistribution` 沒有 entropy 實作，entropy bonus 使用 latent Normal 的 entropy 作穩定近似。舊 checkpoint 的 state shape 沒變，已驗證 `rl_policy.pt` 可以載入。

下一輪建議不要從第三輪的沉默 checkpoint 開始，而是從第二輪仍然敢動的 `training/rl_policy.pt` resume，將 Wrong 懲罰放在中間值 `-0.5`，讓模型重新學會降低誤觸但不直接放棄探索。

建議指令（從 workspace root 執行）：

```powershell
python training\train_rl.py --charts-dir output --holdout 5 --iterations 2000 --rollout-steps 4096 --stage-b-after 1500 --eval-every 25 --early-stop-patience 8 --wrong-penalty -0.5 --lr 1e-4 --resume-from training\rl_policy.pt --save training\rl_policy_round4_balanced.pt
```

這次會使用 weighted accuracy 做 checkpoint 選擇，並在連續 8 次評估沒有改善時提前停止。不要把 `rl_policy_precision.pt` 當 resume 起點，因為它的 `75/634` 結果顯示 policy 已經過度保守。

## 2026-09-25 — 修正 bounded Gaussian 導致的 PPO NaN

第四輪第一次啟動時，rollout 可以完成，但第一次 PPO update 後下一個 minibatch 在 `Normal(loc=...)` 爆出 NaN。追查後不是譜面資料問題，而是 bounded `tanh` action 在 float32 下可能剛好等於速度邊界；重新計算 `log_prob` 時會走 inverse-tanh 的無效邊界，讓 `old_log_prob` 或梯度變成 NaN。

另外，即使沒有直接 NaN，連續 PPO epochs 也可能讓 bounded action 的 log-ratio 過大，造成 policy loss 爆到數萬，這對後續訓練同樣不安全。

**修法**：
- rollout 儲存 `old_log_prob` 前，將 cursor action clamp 到 inverse-tanh 的內部區間。
- minibatch replay 時再次 clamp，保護舊資料與邊界 action。
- PPO log-ratio 限制在 `[-2, 2]`，避免 ratio 失控。

用 `rl_policy.pt` 實際跑完整 1 iteration 驗證：`update()` 正常完成，`policy_loss=0.1092`、`value_loss=14.9298`，沒有 NaN；暫存 checkpoint 已刪除。原本的第四輪長訓練指令現在可以重新執行。

## 2026-09-26 — RL 架構重做：從兩個 Bernoulli 改成互斥三態 action

前五輪反覆在「Wrong 太多」和「Miss 太多」之間擺動，根因不是再找一個 penalty，而是 action space 設計不適合這個 5ms 節奏遊戲：原本每一步獨立取樣 `attack`/`trail` 兩個 Bernoulli，再靠 edge-trigger 把連續的 true 解讀成一次點擊。PPO 必須同時學 action probability、edge transition 和 reward timing，credit assignment 太差。

這次直接重做 RL agent：

- action head 改成一個 Categorical：`0=NOOP`、`1=ATTACK`、`2=TRAIL`，同一 tick 不再同時攻擊和拖曳。
- `TrailRLEnv.step()` 直接執行三態 action，policy 的 categorical log-prob 和環境實際動作一一對應，不再有 Bernoulli edge-trigger 歧義。
- attack timing 分支同時讀 object history 和 own-state（cursor、trail 狀態、ticks since attack），模型能分辨「現在該按」和「剛按過不要再按」。
- PPO 加入 clipped value loss，降低 critic value estimate 失真對 actor 的干擾。
- 新模型的 action head 使用稀疏 no-op prior；初始概率約為 `NOOP=0.98`、`ATTACK=0.01`、`TRAIL=0.01`。均勻初始化在 5ms loop 會立即製造大量 Wrong，並不是有效探索。

這不是輸出端過濾規則，而是 policy 的 action distribution 和 observation/context 的重新設計。冷啟動 smoke test 已通過完整 rollout、PPO update、holdout evaluation；舊 checkpoint 不再是有效的訓練起點，因為 action head 語義已經改變。

## 2026-09-26 — 對照 ybnote-web engine 修正 Judge parity

使用者要求確認 RL simulator 與 `ybnote-web/src/engine` 分毫不差。逐段對照 `PixiApproachCircleManager`、`AiReplayDriver`、`trailSweep.ts`、`obb.ts`、`GameClock` 後，結論是：**不能宣稱完全等價**。已把 Judge docstring 與 `RL_DESIGN.md §16` 改成明確列出 parity 子集及剩餘差異，不再把離線分數說成真遊戲完全重現。

這次已修正：

- 判定邊界：遊戲用 `timeDiff < HIT_WINDOW`、Perfect/Good strict `<`；Python 原本用 `<=`。現在修正並測試 50/100/200ms exact boundary。
- trail 起筆：新 trail press 只測起點，不能把 trail 未按下前的 cursor 路徑掃過去；後續 held movement 才掃 segment。合成測試通過。
- GroupRect 判定核心：有自己的 circle 時以 container exact circle 優先；沒有時依 match-pitch 設定決定 Wrong/chord；chord winners 按最小時間差 anchor，收 event time 差小於 1ms 的 targets，再逐一 score。SAT OBB containment 使用與 engine 一樣的 world-space 投影公式。合成測試覆蓋 container/chord/Wrong/rotated containment。
- Track target circles：原 encoder 會略過 target type `track`。盤點 32 首原始譜面共有 **139 個 interactive track-target events**，集中在 6 首；現在 encoder 以同一個 `getTrackButtonBounds` 輸出 circle 位置，並匯出所有有 handle 的 tracks。Python 另將 track handles 作為 Judge targets，不混入 obstacle observation。新增事件包括戀愛循環 84 個、別墅裡面唱K 44 個等；重新編碼後有效 charts 從 31 增至 32。
- pitch matching：前節所述的 exact/tone FIFO 規則納入 Judge，已重編碼全語料。

validation smoke run 使用 balanced split 和新 sidecars，完整 PPO update/五首 validation 正常結束：track-target event 可載入、track handle 可做 exact hit，match mode 下無 due circle 的 track trigger 不會被錯扣 Wrong。此處的 64-step smoke 指標不是訓練成績。

仍不能稱為「分毫不差」的差異：

- GameClock 在 Pixi render frame 以實際 `deltaSec * gameSpeed` 更新；RL 以固定 5ms step。AI replay 會在 frame callback 一次消化所有到期 entry，命中都用 callback 當下的 game clock，refresh rate/frame pacing 會影響分數。
- GroupRect container/chord 的**runtime ripple side effects**（播放組內 blocks、cross-trigger track、改變後續 track state）尚未完整模擬；目前 Judge 對 circle winner/grade 對齊，不代表副作用狀態完全一致。
- Track handle 命中後 Judge 沒有真的 toggle runner，後續 track-carried geometry 仍取 encoder 假設「所有 seed 準時觸發」預算出的 segments。玩家實際 miss/late/retrigger 後真遊戲狀態可分岔。
- `trailSweep.ts` 有 live-target velocity cache/CCD；Python 只在離散 query time 取 track geometry 並做 cursor segment test，快速移動的 carried object 可能在兩個 timestep 中間穿過 cursor 而漏判。
- Game 最終分數含 combo multiplier、總分 floor-at-zero、Wrong 扣分與 accuracy state；PPO 使用每 note normalized reward，這是學習 objective，不是完整遊戲分數帳本。
- Cursor speed cap 是刻意的人類移動 realism 約束，不是 engine 的硬限制；保留是為了不讓 AI 靠瞬移取巧，不把它宣稱為遊戲本身的物理限制。

因此目前可稱為「判定核心逐步對齊、尚未完整複製 runtime」。要追求逐幀 parity，下一個大工作是把 GameClock/replay scheduling、track runner state、GroupRect ripple 和 trail CCD 納入同一個 event-driven environment；在完成前，validation macro accuracy 仍是 simulator metric，不能保證等於遊戲實測。

### 觀察 1：最佳點總在第一次 eval，之後持續下滑

### 觀察 2：Fall From the Sky 的 Wrong 是結構性的，Judge 沒有錯

Fall 的 deterministic replay 送出 113 次 ATTACK（全為 `f` key），得到 107 hits + 119 Wrong。Wrong 與最近 note 的時間差中位數只有 12.5ms，其中 101 次落在某次命中後 100ms 內。也就是說，**同一次按鍵同時產生一個命中和一個 Wrong**。

根因：這首有**兩個 block 綁 `f`**（`drumBlock-ypj5edif`、`drumBlock-cdt986ek`），兩個都是 `tom/percussion`，但全部 109 個 event 都在 `ypj5edif` 上。對照 `PixiApproachCircleManager.triggerBoundKey()`：它對每個綁該鍵的 block 呼叫 `scoreHit()`；第一個 block 透過 exact 或 tone match 吃掉 circle，第二個找不到 circle，就走 `commit=true` 的 Wrong 分支（-50 分、combo 歸零、`wrongCount+1`）。Python Judge 對 key 也是逐一 score 所有 bound targets，所以 **simulator 與遊戲一致**：真遊戲裡用 `f` 打這首，每下也會附帶一個 Wrong。

這代表：只要按鍵，Fall 的 accuracy 上限約為 `(109 − 0.25×109)/109 = 75%`。避開 Wrong 的唯一方法是直接用滑鼠點該 block（mouse click 只 score 游標碰到的 target）。但目前 action space 做不到：`ATTACK` 只要可見 target 有 keyBinding 就一律送 key，policy 沒有「改用點擊」的選項。這是 action encoding 的限制，不是 policy 學錯，也不是 parity 問題。

### 下一步

1. **Fall 類譜面的 action 路徑**（需決定）：(a) `ATTACK` 在游標已覆蓋有綁鍵的 target 時改送 mouse click、否則送 key；或 (b) 新增第四個動作 `CLICK`，讓 policy 自己選 key 還是 click。(a) 不改 action head，舊 checkpoint 可直接沿用；(b) 表達力較完整，但要重新初始化 action head。
2. **抓峰值**：續訓改 `--eval-every 5`（patience 相應改成約 10），並把 `--lr` 降到 `2e-5`；或先凍結 actor、只更新 critic 幾個 iteration，讓 value function 對齊新 Judge，再解凍 actor。
3. NIGHT DANCER（M:173、W:88）與 CHROMANCE（M:154）的主要損失仍是 Miss，也就是 cursor 沒到位。D4 augmentation 已開，這部分要看續訓是否改善，才決定要不要動 cursor head/速度上限。

## 2026-09-26 — CLICK / KEY split：點擊還是按鍵，交給 policy 決定

上一節的 Fall 診斷只說對一半：**有綁鍵的 object 一樣可以直接點**。對照 `ybnote-web/src/engine`：

- 點擊（`AimGestureController` tap → `checkTrailIntersection(x,y,x,y,true)` → `scoreHit`）只 score 游標碰到的 object，完全不看它有沒有 keyBinding。
- 按綁定鍵（`onKeyDown` → `triggerBoundKey`）會 score **所有**綁同鍵的 block/groupRect/track；沒有 due circle 的每一個都各算一個 Wrong。未綁定的鍵等於在游標處攻擊。
- `AiReplayDriver` 本來就把 `attack`（點擊）和 `keybindsFired`（按鍵）分成兩個獨立欄位。

所以問題出在 `rl_env` 自己加的解碼：「目標有鍵就強制送鍵」。遊戲規則沒有這個限制。固定規則也不對：像 Fall 這種兩個 block 同鍵、只有一個有 note 的情況，點擊比較好；故意一鍵綁多顆的和弦，或目標離游標太遠時，按鍵比較好。因此改成讓 policy 自己選：

- **動作**：`NOOP / CLICK / TRAIL / KEY`（index 0–2 保持原意，KEY=3）。`KEY` 仍從 observation 讀出目前目標的鍵；目標沒鍵時等同點擊，和遊戲按未綁定鍵的行為一致。
- **Policy head 採分解式**：`action_head` 決定何時動作（no-op/press/trail），新的 `input_path_head`（Bernoulli）決定 press 用點擊還是按鍵。原本考慮的是平坦 4-way head，但這樣 deterministic argmax 會把 ATTACK 的機率拆成兩半，各自可能低於 NOOP，模型就突然不按了。
- **新 observation 欄位 `key_share`**：每個 slot 記錄「這個 note 的鍵另外還綁了幾個 object」（`min(extra,4)/4`）。玩家看得到每個 block 上的鍵名，但 observation 只列出有 note due 的 object；沒有這個欄位，Fall 那顆沒有 note 的 `f` block 對模型是隱形的。由 env 附加，不改 frames.csv 或 supervised pipeline。Judge 的按鍵路徑也改用同一個 `ChartData.key_bound_targets()`，兩邊不會各算各的。
- **舊 checkpoint 無損遷移**（`migrate_pre_split_checkpoint`）：輸入層新欄位的權重設為 0，when-head 原樣保留，how-head 的 logit 從 0 開始。deterministic 平手時選 KEY，所以遷移後的行為等於舊 ATTACK；sampling 時則對有鍵的目標 50/50 探索點擊和按鍵。
- **`export_replay.py --policy rl`**：直接用 `TrailRLEnv` 跑 deterministic rollout，把 env 解析出的動作原樣寫入 replay（CLICK→`attack`，KEY→`keybindsFired`），確保離線評分和遊戲實際執行的是同一串輸入。

驗證：

- 遷移前後，3000 個真實 observation 的 cursor/action/value 輸出最大差 `7.6e-6`（浮點誤差；其中 2879 個 observation 的 key_share 非零）。
- 遷移後的 v3 做 deterministic validation，結果與遷移前完全相同：`321/819`、macro `25.83%`。
- Fall 腳本測試（在每個 note 時間把游標放到目標 block 上）：CLICK → `Perfect 109、Wrong 0`；KEY → `Perfect 107、Bad 2、Wrong 109`。遊戲規則下 Fall 可以拿滿分，前提是用點的。
- `export_replay --policy rl` 對 Fall 輸出 113 個 keybind、0 個 attack，simulator 判定與 validation 一致。
- PPO smoke（resume v3，2 iterations）：rollout 同時出現 click/key，checkpoint metadata 帶 `action_space=noop_click_trail_key`、`features_per_obj=73`。

## 2026-09-26 — Trail 改成狀態切換、按壓可在 trail 中進行；修正座標 bounds

### Trail：原設計不正確

上一節的 `NOOP / CLICK / TRAIL / KEY` 仍把 trail 當成**每個 tick 重選一次**的互斥動作，因此有兩個問題：

1. **按不住**：要維持 stroke，必須每 5ms 都抽到 TRAIL。每 tick 機率 p 時，連續 40 tick（200ms）的機率只有 p⁴⁰；只要一 tick 沒抽到就放開，而放開會清空 intersected，重按又得重新走 `commit=true` 的起筆檢查，斷掉那一 tick 的路徑也不會被掃到。實測 v3 在 5 首 validation 上 P(trail) 最高只有 0.32%，deterministic 模式 0 次 stroke，抽樣出的 trail 全是孤立單一 tick，效果等同點一下。
2. **trail 中不能 click/key**：互斥動作一選 CLICK/KEY 就放開 trail。但遊戲允許：按住時再按滑鼠或未綁定鍵，走 `discreteSecondaryHit`（tap）；綁定鍵一律走 `triggerBoundKey`。兩者都不會中斷 stroke。`AiReplayDriver` 同一個 entry 也能同時帶 `attack`、`keybindsFired`、`trailHeld`。

**新設計**：每 tick 的動作拆成兩個獨立部分，可在同一 tick 同時發生：

- press：none / CLICK / KEY（沿用 when-head + how-head）
- trail toggle：Bernoulli「切換 held 狀態」。stroke 開始後會一直按著，直到 policy 明確放開。toggle head 讀完整 trunk 加 timing branch，按住期間再加一個可學習的 `trail_release_offset`，讓「開始」和「放開」各有初始 prior（約 0.25%/tick 與 3%/tick）。
- Judge 補上 tap 的 `clearIntersected()` 語義：點擊後 intersected 集合改為「這次點到的物件」。這在按著 trail 的同時點擊才有影響。
- 動作編碼成單一 int（`press + 3*toggle`），`ppo.py` 不用改。訓練 log 改印 press 分布、toggle 次數，以及 rollout 中 trail 按著的比例。
- v3 遷移：when-head 保留 no-op/attack 兩行，舊 trail 行刪除；v3 的 trail 從來不是 argmax，所以 no-op/press 決策不變。how-head 與 toggle head 從中性值開始。

### 修正座標 bounds（重大 parity bug）

測 trail 時發現 Fall 的 normalization bounds 只有 **2×2 world units**：`computeBounds` 只看 note 位置，而 Fall 的 109 個 note 全在同一點。cursor 被限制在 [0,1]，也就是 60×60 block 內的 2×2 區域：永遠離不開那個 block，另外 7 個 block（含 5 個綁鍵的）完全碰不到。盤點全部 32 首：

- Honeypie（720×2）、我們打他（360×2）、levan Polkka（288×2）：note 都在同一橫排，y 方向只剩 2 world units，連一個 block 都裝不下。
- 戀愛循環：y 值只有約 1e-14 的浮點雜訊，`(maxY-minY)*0.1 || 1` 的 fallback 沒觸發，y 範圍幾乎為 0。
- 其餘 chart 多半 x/y 比例不同（最高 4.3:1），同一個 normalized 距離在兩軸代表不同的 world 長度，D4 旋轉與 cursor 速度上限在兩軸也不等價。

**修正**（`encodeFrames.js computeBounds`）：bounds 涵蓋所有可互動物件，包括 note、所有 enabled block/groupRect（與 collidables 相同的過濾條件）、被 track 帶動物件在實際移動期間的路徑（每 50ms 取樣，含旋轉外接圓），以及 track handle。四周各留一個 block（60）的邊距，並取**正方形**，兩軸共用同一 world 比例。重新編碼 32 首後，每首的 enabled collidable 都在可達範圍內，note 數不變。新舊 span 例：Fall 2×2→850×850、Honeypie 720×2→1462×1462、NIGHT DANCER 1468×540→1740×1740。舊輸出暫留在 `output_prev_bounds/`（未追蹤；嘗試移出 repo 時 permission denied）。

**後果**：
- 所有 normalized 座標都變了。遷移後的 v3 在新座標下 deterministic validation 從 macro `25.83%` 掉到 **`12.18%`**（176/819）。舊的 25.83% 是在遊戲裡不存在的幾何上量到的，例如 Honeypie 的 y 軸被壓成 2 units，所以兩者不可比。**12.18% 才是 v4 的起點。**
- `CURSOR_MAX_SPEED_NORM_PER_STEP=0.05` 以 normalized 單位定義，換算成 world 速度原本就隨 chart 大小而變；bounds 變大的 chart，等效 world 速度也跟著變大（例：lovely 478→3461）。這是刻意加的人類 realism 約束，不是遊戲規則，這次沒動，但該以 world/螢幕單位重新定義，需另外決定。

### 驗證

- 遷移前後（新編碼）cursor/value/when logits 最大差 `2.9e-6`；遷移後 P(toggle) 最高 0.25%，deterministic 不會觸發 toggle。

## 2026-09-26 — World-unit cursor：速度上限改用 world 單位，加上移動體力懲罰

bounds 修正後，原本以 normalized 單位定義的速度上限（0.05/tick）換成 world 速度會因 chart 而差約 10 倍：Rickroll 的 span 是 351，約 3500 world/s；lovely 是 3461，約 34600 world/s。使用者提議拿掉上限、改由體力懲罰讓 AI 自己控制力道。最後採兩者並用：

- **硬上限改用 world 單位**：`RL_CURSOR_MAX_SPEED_WORLD_PER_S = 8000`（每 tick 40 world units），每首 chart 都是同一個物理速度。只靠懲罰仍需要 action 邊界（tanh 必須縮放到某個值）；quadratic 懲罰在大獎勵面前也擋不住瞬移。保留一個「人手做得到」的上限，才能保證 replay 看起來合理。這是 realism 約束，不是遊戲規則。
- **Cursor action 的意義**：tanh 輸出 = 上限的比例（每首 chart 意義相同），env 再乘以 `reach = 上限每 tick / chart world span` 換成 normalized 位移。own-state 新增 `reach`（×10），讓 policy 知道在這首 chart 全速一 tick 能走多遠。
- **體力懲罰**：每 tick `0.002 × (速度/上限)²`。平方項讓「快速少 tick」比「平滑多 tick」更貴，閒置抖動也有代價；全速甩 100ms 的成本 0.04，遠低於一個 Perfect。只影響訓練 reward，validation/checkpoint 仍只看 Judge 判定。
- **v3 遷移**：輸入層為 `reach` 補零權重欄位（沿用同一套 relayout，own-state 由 4 變 5）。cursor head 原樣保留，但輸出意義從 0.05 normalized/tick 變成上限比例，在 span 約 800 的 chart 上兩者等速；更大的 chart 相對變慢，更小的變快。

驗證：

- 遷移前後 cursor/value/when logits 最大差 `2.9e-6`。
- 對三首 span 差很多的 chart 要求 5 倍上限的位移（Fall 850、lovely 3461、Rickroll 351），實際都恰好移動 40.0 world units；全速懲罰 -0.0020，30% 速度 -0.00018。
- CLICK/KEY、持續 stroke 測試結果不變。
- 新基準：遷移後 v3 在新座標加 world-unit cursor 下，deterministic validation macro **`12.42%`**（173/819）。
- critic warmup：15 次 critic-only iteration 的 value_loss 從 4–5 降到 <1，但因每次 rollout 抽到的 chart 不同而偶有尖峰（最高 13）。v4 用 30 次 warmup。

### 疑似系統性原因：rollout 高度相關

`train_rl.py` 每個 iteration 收 4096 步，env 只在整首 chart 跑完時才換 chart（`if env.done:` 才重抽）。full-chart episode 動輒 1–4 萬步，所以**連續 3–10 個 iteration 的 PPO update 都只用同一首 chart 的連續片段**。每次 update 都朝「眼前這首」優化，換 chart 前 policy 早已偏離其他 chart 的好區域；value_loss 忽高忽低（0.07↔13），也符合 critic 每幾個 iteration 就面對一首新 chart 的情況。這很可能是每一輪都「早期見頂、之後退化」的主因。標準做法是同時跑多個 env（不同 chart），每個 update 的 batch 混合多首 chart 的片段。

### 修正：多 env 並行 rollout

- `train_rl.py --num-envs N`（預設 8）：同時維持 N 個 episode，盡量各在不同 chart 上（重抽時優先選其他 env 沒在用的 chart）。每次 update 的 `--rollout-steps` 平均分給 N 個 env（4096/8 = 512 步），所以一個 batch 固定混合 8 首 chart 的片段。每個 env 的 episode 跨 iteration 繼續跑，跑完才換 chart。
- `PPOTrainer.update` 改收多個 buffer：每個 buffer 是一條連續軌跡，GAE 逐 buffer 計算並各自用該 env 的最後 observation bootstrap（buffer 最後一步若是 episode 結束就 bootstrap 0），算完才串接做 PPO epoch。reward normalization 統計所有 buffer。
- smoke：從 v4 最佳 checkpoint 起跑，4 env × 256 步正常更新；Stage A 短 window 下 episode 中途結束、換 chart 的路徑觸發 12 次，沒有錯誤。

## 2026-09-26 — 規劃：ybnote-web 多模型 AI replay 比較（尚未實作）

目標：在 ybnote-web 做一個 admin UI，讓多個訓練階段的模型在同一首譜上疊加播放，用來做比較影片。單一模型時鏡頭跟隨游標、使用者可縮放；多個模型時每個游標不同顏色，鏡頭改成自由模式（任意平移、縮放）。以下是規劃 agent 讀過兩個 repo 後的結論。

### 現況與限制

- 現在的單一 replay（`AiReplayDriver`）**沒有畫 AI 游標**：只驅動 trail 與判定，並用 `followCamera()` 讓畫面中心跟著游標；只有 CROSSHAIR 模式的中央準星剛好等於游標位置。彩色游標要從零做。
- `PixiTrailManager` 只有一條筆畫，顏色寫死，淡出用 `performance.now()`（不是 chart time）。
- 判定與全域狀態綁死：`scoreHit` 會把 circle 從 activeCircles 移除並直接寫 `useGameStore`（分數、combo、track toggle），同一個 engine 無法同時跑 N 份獨立判定。
- **暫停會弄丟 note**：非 PLAY phase 時 `activeCircles` 會被清空，暫停再繼續會讓結果失真。
- 相機：PLAY 中中鍵平移與滾輪縮放本來就能用，但 CROSSHAIR 模式滾輪的 pivot 固定在畫面中心。
- checkpoint 相容性：v4/v5 直接可跑；categorical v1–v3 可經 `migrate_pre_split_checkpoint`；`dl_policy_multi`/`dl_policy_noaug_test` 與 engineered 可跑。round1/precision/round4/`rl_policy.pt`（Bernoulli head、沒有 `attack_state_trunk`）與 `dl_policy.pt`（32 維輸入）需要另寫 adapter。
- 舊權重放在目前 env（正方形 bounds、world-unit cursor）跑出來的表現**不是它們當時的行為**，影片需標註。

### 方案與建議

- **模型在哪跑**：採「離線批次」。PyTorch 無法在 Cloudflare worker 上跑；ONNX + onnxruntime-web 需要用 TS 重寫整條 observation pipeline 與 Judge（已判定 circle 要隱藏），parity 風險過高，不建議。可選的後續是本機 Python helper（localhost，需處理 CORS/PNA）。
- **多條 log 同時播**：多條時真實 engine 不計分（`spectatorMode`），所有模型都以 ghost 游標顯示；每個模型的判定來自預先算好的判定軌。第一階段用 Python Judge 算（標示 `python-sim`），第二階段在網頁上逐一以單條模式重跑，取得與遊戲一致的判定（`web-engine`）。單條時維持現在由真實 engine 判定。
- **繪製**：新增 `PixiAiReplayOverlayManager`，每個模型有自己的彩色游標、trail 筆畫緩衝（用 chart time 淡出）與打擊特效；legend HUD 顯示每個模型的即時 score/combo/PGBMW/accuracy。
- **相機**：單條預設跟隨＋縮放，可切自由；多條預設自由，AI 模式下左鍵也能平移，滾輪 pivot 改為滑鼠位置；另加 Fit chart、跟隨指定模型。
- **錄影**：clean mode 隱藏 UI 只留 legend；回放只由 chart time 決定，建議 1x。
- **資料格式**：比較 bundle `ybnote-compare/1`（`.json.gz`），內含 chart 資訊（title、levelId、fingerprint、bounds）與每個模型的 label/stage/color/checkpoint/meta。log 以欄位式存放（t/x/y/旗標），判定軌帶 blockId（由 events.json 的物件 id 對回）。

## 2026-09-26 — 完美玩家測試：修正「起筆點在 block 上時 groupRect 不計分」

為分辨「模型打不到」與「模擬器／編碼有問題」，對 32 首譜各跑一次完美玩家：每個 note 時間把游標放到 note 位置並 CLICK。31 首約 97–100% 命中，唯一明顯異常的是 **JAWNY - Honeypie：160 個全中，卻同時有 161 個 Wrong**。

**根因**：Honeypie 的每個 note block 都被一個被 track 帶動的 groupRect 包住，點一下同時碰到兩者：block 命中，groupRect 找不到 due circle 就記 Wrong。遊戲的 `trailSweep.ts sweepTrailSegment` 有一條 Judge 沒實作的規則：

```ts
if (!wasIntersected && !(isFirstPoint && startedOnBlock)) { /* fire groupRect */ }
```

起筆點（tap，或 stroke 的第一點）落在任何 block 上時，groupRect 只加入 intersectedRef、不觸發。所以在遊戲裡點 Honeypie 的 block 只會命中 block。

**修正**：`reward.py` 新增 `Judge._scored_on_first_point()`；點擊與 stroke 起筆時，只要碰到的目標中有 block，就把 groupRect 從計分名單移除，但仍記入 `_inside_collidables`，之後在 rect 內移動也不會觸發。修正後完美玩家在 Honeypie：`Perfect 160、Wrong 0`。

其他小異常都不是 bug：

- 朴樹（4 Miss）、戀愛循環（1 Miss）：同一時間有 note 在不同位置（和弦），完美玩家一次只點一個位置。
- 只因為你（7 Wrong）：點擊位置和另一個沒有 due note 的 block（`noteblock-dkuzrvgi`）重疊，遊戲同樣會對碰到的每個 block 計分。

這個修正改變了訓練 reward 與 validation 判定（Honeypie 是 validation 譜）。先前各版在 Honeypie 的低分，部分是這個 bug 造成的：每次點擊都被扣一個 Wrong，policy 學到在那首少點。
